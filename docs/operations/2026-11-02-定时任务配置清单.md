## 0. 背景与目标

服务跑在 Render 免费实例上，数据库在 Supabase。Render 免费 web service 空闲 15 分钟会休眠，休眠时进程停止，两个后台服务（定投执行 `PlanSchedulerService`、行情刷新 `QuoteRefreshSchedulerService`）随之停止。

本次配置要达到两个目标：

1. **每天北京时间 12:30 可靠执行到期定投**——由 GitHub Actions 唤醒服务并调用 `POST /api/cron/plans/run`。
2. **平时保持服务唤醒**——由 GitHub Actions 每 10 分钟打一次 `/api/health`，消除冷启动等待。仓库是公开的，Actions 分钟数不计量，可以直接开启。

服务端新增的机器入口用共享令牌鉴权（请求头 `X-Cron-Token`，配置键 `Cron:Token` / 环境变量 `Cron__Token`），不走登录 Cookie。未配置令牌时该入口返回 503，即自动关闭。

## 3. 执行步骤

每步都给出「命令」「期望输出」「失败怎么办」。按顺序做，不要跳步。

### 步骤 1　准备环境变量

```bash
export REPO="zhousl0801/asset-manager"
export BASE_URL="https://asset-manager-api.onrender.com"   # 用 1.3 查到的实际地址，结尾不要斜杠
export SERVICE_ID=""                                        # Render 服务 ID，见下方说明
```

`SERVICE_ID` 的取法（任选其一）：

- Dashboard 打开该服务，看浏览器地址栏 `https://dashboard.render.com/web/srv-xxxxxxxxxxxx`，`srv-` 开头那串就是。
- 或者用 API 按名字查：

```bash
curl -s "https://api.render.com/v1/services?name=asset-manager-api&limit=20" \
  -H "Authorization: Bearer $RENDER_API_KEY" \
  | grep -o '"id":"srv-[a-z0-9]*"' | head -1
```

**期望**：`SERVICE_ID` 是一个 `srv-` 开头的字符串。
**失败**：拿不到就改用 Dashboard 手工操作（见步骤 3 的方式 A），不影响后续步骤。

### 步骤 2　核对代码分支

```bash
git fetch origin
git log --oneline -3 origin/work
git log --oneline -3 origin/main
```

**期望**：`origin/work` 最新一条是 `39aec92`。
**失败**：看不到该提交 → 停下报告，不要自行 merge 或 cherry-pick。

### 步骤 3　生成共享令牌

```bash
TOKEN=$(openssl rand -hex 32)
echo "令牌长度: ${#TOKEN}"    # 只打印长度，不打印值
```

**期望**：输出 `令牌长度: 64`。
**失败**：`openssl` 不可用则改用 `python3 -c "import secrets;print(secrets.token_hex(32))"`，同样只装进变量、不打印。

> ⚠️ 这个变量只存在于当前 shell 会话。**不要** `echo $TOKEN`、**不要** `set -x`、**不要**写进任何文件。若中途 shell 断开，重新生成一对新值并同时更新 Render 和 GitHub 即可（旧值作废不影响数据）。

### 步骤 4　写入 Render 环境变量

**方式 A：Dashboard 手工（推荐，最稳）**

1. Render Dashboard → 服务 `asset-manager-api` → 左侧 **Environment**
2. 新增一行：Key = `Cron__Token`，Value = 步骤 3 生成的令牌
3. 保存，Render 会自动触发一次重新部署

**方式 B：Render API**

```bash
curl -s -X PUT "https://api.render.com/v1/services/$SERVICE_ID/env-vars/Cron__Token" \
  -H "Authorization: Bearer $RENDER_API_KEY" \
  -H "Content-Type: application/json" \
  -d "{\"value\": \"$TOKEN\"}"
```

然后触发重新部署：

```bash
curl -s -X POST "https://api.render.com/v1/services/$SERVICE_ID/deploys" \
  -H "Authorization: Bearer $RENDER_API_KEY" \
  -H "Content-Type: application/json" -d '{"clearCache":"do_not_clear"}'
```

**等待部署完成**（两种方式都要等，环境变量只在部署后生效）：

```bash
for i in $(seq 1 40); do
  code=$(curl -s -o /dev/null -w '%{http_code}' --max-time 20 "$BASE_URL/api/health" || true)
  echo "第 $i 次探活：HTTP $code"
  [ "$code" = "200" ] && break
  sleep 15
done
```

**期望**：最终出现 `HTTP 200`。
**失败**：
- 一直 `000` / 超时 → 部署还在进行，等满 10 分钟再看 Dashboard 的 Logs。
- 连续 `502` → 部署失败，去 Dashboard 看 Logs 里的启动异常。

### 步骤 5　写入 GitHub Secrets

```bash
gh secret set APP_BASE_URL --repo "$REPO" --body "$BASE_URL"
gh secret set CRON_TOKEN   --repo "$REPO" --body "$TOKEN"

gh secret list --repo "$REPO"
```

**期望**：`gh secret list` 同时列出 `APP_BASE_URL` 和 `CRON_TOKEN`（值不会显示，这是正常的）。
**失败**：报权限不足 → 确认 `gh auth status` 里当前账号对该仓库有 admin 权限。

### 步骤 6　打开保活开关

```bash
gh variable set KEEP_WARM_ENABLED --repo "$REPO" --body "true"
gh variable list --repo "$REPO"
```

**期望**：列表中出现 `KEEP_WARM_ENABLED  true`。
**失败**：同上，检查权限。

### 步骤 7　合并到 main 并推送

GitHub 的 `schedule` 只在**默认分支**生效，必须让 `main` 包含本次提交。

```bash
git checkout main
git pull --ff-only origin main
git merge --ff-only work          # 若报错说明 main 有 work 未包含的提交，停下报告
git push origin main
git rev-parse HEAD                # 应等于 39aec92 的完整 sha
git checkout work
```

**期望**：推送成功，`git rev-parse HEAD` 与 `git rev-parse origin/work` 一致。
**失败**：`--ff-only` 失败说明有分叉 → 停下报告，不要强推。

等 CI 通过（push 到 main 会触发 `ci.yml`）：

```bash
gh run list --repo "$REPO" --workflow ci.yml --limit 2
gh run watch "$(gh run list --repo "$REPO" --workflow ci.yml --limit 1 --json databaseId -q '.[0].databaseId')" --repo "$REPO"
```

**期望**：两个 job（后端构建与测试、前端检查测试构建）都是成功。

### 步骤 8　手动触发一次验收

不必等到 12:30，现在就跑一遍：

```bash
gh workflow run daily-plan-run.yml --repo "$REPO"
sleep 10
gh run list --repo "$REPO" --workflow daily-plan-run.yml --limit 1
gh run watch "$(gh run list --repo "$REPO" --workflow daily-plan-run.yml --limit 1 --json databaseId -q '.[0].databaseId')" --repo "$REPO" --exit-status
gh run view "$(gh run list --repo "$REPO" --workflow daily-plan-run.yml --limit 1 --json databaseId -q '.[0].databaseId')" --repo "$REPO" --log
```

**期望的日志片段**（顺序出现）：

```
第 1 次探活：HTTP 200
服务已就绪
第 1 次触发：HTTP 200
{"createdOccurrences":0,"completed":0,"waiting":0,"failed":0}
```

**判读**：

| 看到 | 含义 | 处理 |
|---|---|---|
| `HTTP 200` + 全 0 | 跑通了，当前没有到期的期次 | 正常，无需处理 |
| `HTTP 401` | Render 的 `Cron__Token` 与 GitHub 的 `CRON_TOKEN` 不一致 | 重新生成一对，两边同时更新 |
| `HTTP 503` | Render 没配 `Cron__Token`，或配了但没重新部署 | 配置并重新部署 |
| 探活 5 分钟仍不 200 | 服务起不来 | 去 Render Logs 查启动异常 |

> 白天手动触发时各计数通常全为 0 是**正常现象**：12:30 的期次当天已经执行过或还没到点。真正的验收标准是 `HTTP 200`。

### 步骤 9　确认保活已在运行

```bash
gh run list --repo "$REPO" --workflow keep-warm.yml --limit 3
```

**期望**：最近几条都在跑/成功（每 10 分钟一次，最新记录不应超过 15 分钟）。
**失败**：一直是 skipped → 检查 `KEEP_WARM_ENABLED` 是否真的是 `true`（大小写敏感）。

```bash

unset RENDER_API_KEY    # 如果临时 export 过
```

**期望**：`echo "${TOKEN:-空}"` 输出 `空`。

## 7. 已知限制（不用处理，只需知道）

- GitHub 定时任务在仓库连续 **60 天无提交**后会自动停用，需要手动重新启用。
- Actions 的 `schedule` 不保证准点，高峰可能延迟十几分钟。定投靠幂等补齐，日期不受影响。
- Render 免费每月 **750 实例小时**，全天保活约 730 小时，刚好够、没有余量。若当月多跑一个免费服务，额度会不够，表现为服务被暂停。
- 保活只影响「打开 APP 时要不要等冷启动」；**定投的正确性只依赖 12:30 那个工作流**，即使保活关掉也不影响定投执行。
