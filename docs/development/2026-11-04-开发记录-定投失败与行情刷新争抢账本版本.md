# 2026-11-04 定投失败与行情刷新争抢账本版本

## 现象

11-03 的四条每交易日定投，两条成功、两条失败：

| 期次 | 计划 | 金额 | 结果 | 时刻（UTC） |
| --- | --- | --- | --- | --- |
| T2026-11-03 | 银华海外数字经济 | 200.00 | 失败 | 05:00:26.8 |
| T2026-11-03 | 建信新兴市场 | 100.00 | 失败 | 05:00:27.9 |
| T2026-11-03 | 大成纳斯达克100 | 640.00 | 成功 | 05:00:28.8 |
| T2026-11-03 | 国富全球科技 | 100.00 | 成功 | 05:00:29.7 |

失败信息是 `数据已被其他操作修改，请核实保存结果或刷新后重试。`，来自 `MutationExecutor` 捕获的 `DbUpdateConcurrencyException`：`ledgers.version` 在读取和保存之间被别人改掉了。

四个期次在同一批里按 `PlanId` 顺序执行，前两条判冲突、随后两条立刻成功，说明冲突源在这两秒钟内结束。

## 成因

Render 免费实例 15 分钟无流量就休眠，12:30 时实例是睡着的，靠 GitHub Actions 每 10 秒探活唤醒。醒来的一瞬间两个后台任务同时启动：

- `PlanSchedulerService`：`do/while` 首轮立即执行，生成四个期次（05:00:16）。
- `QuoteRefreshSchedulerService`：`RunOnStartup: true`，立刻跑全量刷新。

行情刷新**不参与计划执行的那把锁**（`PlanExecutionService.RunLock` 只保护计划侧），而且每刷一只基金都会 `ledger.Touch(now)` + 保存，不管净值有没有变化：

```csharp
position.RecordQuoteSyncAttempt(now, quote.Source, null);
ledger.Touch(now);                       // 净值没变也推进版本号
await _ledgerRepository.SaveChangesAsync(cancellationToken);
```

11 月 3 日当天净值还没披露，刷新拿回来的还是 11-02 的净值，判为无变化、不落 `price_observations`，但版本号照样涨了八次。正在执行的定投撞上就判死。

伤害不止于丢一天：失败期次没有重试机制，`GetPendingOccurrencesAsync` 只捞 `Pending`，判成 `Failed` 就永久躺下。

## 修改

### 1. 行情刷新没有实质变化就不写账本

基金、积存金、股票三处刷新统一改成只在真的记录到新行情（`updated == true`）时才 `ledger.Touch`；取行情失败时只记录尝试结果，不再推进版本号。

版本号仍然会在真有新净值/新报价时变化，所以前端发现的「数据变了」信号不受影响；变化频率从「每小时每只资产」降到「每天每只资产一次」。

### 2. 定投失败自动重试

- `PlanOccurrence` 新增 `AttemptCount`，每次执行（含手动重试）都会 `BeginAttempt` 记账；列 `attempt_count` 由迁移 `20261104041359_AddPlanOccurrenceAttemptCount` 加入，默认 0。
- 新增 `CanAutoRetry(businessDate)`：只有**到期当天**失败、且尝试次数未到上限（`MaximumAutoAttempts = 3`）的期次才会被自动重跑。
- `PlanRepository.GetPendingOccurrencesAsync` 同时取回失败期次，由 `PlanExecutionService` 按上面的规则过滤；跨天的失败期次仍然留在失败态等人判断，不静默补买旧期次。
- 重跑沿用期次 Id 作为幂等键，重复执行不会重复入账；如果上一轮其实已经入账（只是回写期次失败），重跑会命中回执直接判完成。

## 验证

- 新增 `QuoteRefreshServiceTests`：净值不变、取行情失败、积存金报价不变三种情况都不再推进 `ledgers.version`。
- 新增 `PlanExecutionTests`：当天失败次日运行可自动完成（尝试次数 1 → 2）；前一天的失败期次不重试；达到 3 次后不再重试。三条都断言现金余额，确认没有重复入账。
- `BackupPlanOccurrence` 补 `AttemptCount`，备份完整性测试随即通过（漏字段会被 `BackupDtos_CoverEveryScalarEntityProperty` 拦住）。
- 后端 **347 项通过、18 项真实 PostgreSQL 用例跳过**。
- 迁移已用 `dotnet ef database update` 应用到 Supabase 真库（生产环境启动时 `Program.cs` 会自己迁移，本地 Development 不会），历史期次 `attempt_count` 全为 0。

## 遗留

- 11-03 那两条失败期次不属于「当天」，不会被自动重试，需要人工决定是否按 11-03 补记。
- 自动重试依赖进程醒着：如果一个 60 秒周期内都没醒，当天就没机会再试。极端情况下仍需要手动补记。
